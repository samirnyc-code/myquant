## Root cause chain (verified)

1. **The trigger daemon's heartbeat went stale 3 separate times** this morning —
   `desk_watchdog.py`'s hang detector (`check_trigger_daemon`, threshold 360s)
   flagged it HUNG at **08:40:20, 08:40:25, and 08:50:32 CT**
   (`data/_catalog/logs/desk_watchdog.log`, timestamps already CT — `now()` there
   is `dt.datetime.now(CT)`, no conversion needed).
2. At 08:40 the watchdog found **two distinct hung process-pairs alive at once**
   (8 PIDs across two "killing hung pair" actions 5 seconds apart) — more than
   one daemon instance was already running concurrently before the watchdog even
   acted.
3. Each hang triggered a kill + restart via the `"MyQuant Trigger Daemon"`
   scheduled task.
4. Each restart landed inside `run_at_ct.py`'s ±25-min "on time" window around
   the 08:29 CT target (confirmed via `data/options_sim/trigger_daemon_sched.log`:
   `RUN` at 08:29, 08:29, 08:29, then again 08:40, 08:40, 08:50 — none skipped).
   So the DST dual-trigger safety mechanism (two Scheduled-Task triggers 1h apart,
   intended to guarantee exactly one real launch per day across the EU/US DST
   mismatch week) was not the bug here — `run_at_ct.py` correctly let every
   watchdog-forced restart through because they were all genuinely within the
   on-time window, not because the dual trigger misfired twice.
5. Each fresh `options_trigger_daemon.py` instance reloaded
   `gameplan_20261030.json` and re-fired every trigger it still saw as
   not-yet-`fired` on disk → the 2-3x duplicate fills.

## Why the daemon hung in the first place (sourced, not fully proven for today)

`scripts/desk_watchdog.py:66-68`'s own comment documents the mechanism: the
`trig_hb` staleness threshold (360s slow / 300s fast) was already widened once
before, on 2026-09-17, because `manage_open()` blocks ~2-3 min sequentially
quoting every leg of every open position — that alone pushed heartbeat staleness
to 191s during the **14:45 EOD close burst**. The comment only names the EOD-side
burst, but this morning's **entry burst** (10 fresh combo fills in 9 minutes,
08:31-08:39 CT) is the same shape of event on the open side — each fill becomes
eligible for `manage_open`'s exit-check ~60s later, so the same sequential-leg-
quoting block plausibly pushed heartbeat staleness past 360s. **Not proven**: no
captured stdout from today's killed PIDs exists to confirm this directly, but it
is the documented mechanism for this exact symptom and fits the timing.

## Open items (not yet acted on — flagging before touching live desk infra)

1. **Daemon dedup is purely in-process** (`gameplan_*.json`'s `fired` flag,
   written by whichever instance is currently running) — there is no
   cross-process or trade-log-level guard stopping a second instance from
   re-firing a strategy_id that's already in `trades.parquet` for the day.
   Candidate fix: before firing, check `trades.parquet` for an existing
   entry with the same `strategy_id` + today's date.
2. **The watchdog can issue a second restart while a prior restart's daemon is
   still alive** (the 2 overlapping pairs at 08:40) — kill-then-relaunch isn't
   verified atomic across the launcher/worker process-pair. Candidate fix: wait
   for confirmed process death (poll, not fire-and-forget `taskkill`) before
   relaunching, or hold a lock file across the kill+restart.
3. **`trig_hb` threshold may need the same entry-burst allowance the EOD burst
   already got** — or `manage_open` needs to heartbeat mid-batch instead of only
   once per outer loop iteration, so a long leg-quoting pass doesn't look hung.
4. **`options_mark.py` has no restart-cap-hit alerting beyond the repeating toast**
   — it died 5x in 40 minutes with no root cause captured. Needs its own
   exception logging before the next occurrence to actually diagnose it.
5. **Restart cap (5/day) left the desk flying blind on live P&L for ~4.5 hours**
   with no escalation beyond a repeating notification. Worth a harder alert
   (not just another toast) when a component is permanently down for the day.

None of the above have been implemented. Waiting on user direction on which (if
any) to fix.
